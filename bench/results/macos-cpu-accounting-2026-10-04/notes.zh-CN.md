# CPU 计时交叉校验与组合版本硬件计数

本次推进的是定位 CPU 波动的证据，不是宣布 CPU 占用优化验收完成。候选仍是 codex/client-cpu-memory 的 84e257d；同一 main d60c18a 服务端；二进制未重新编译或修改，签名后的哈希见 binaries.json。启动时观察到系统后台进程高负载，但只有边界观察，没有连续后台负载记录，不能据此确定此前波动原因。

## 计时与采样实现

新增 bench/verify_macos_cpu_clock.py，通过独立子进程的 time.process_time() 与父进程 proc_pid_rusage 的差值交叉校验。3 次两秒忙循环以及前后两次睡眠均通过；保存的忙循环差值为 0.0922、0.0618、0.0519 毫秒，未发现 Mach 时间单位换算问题。已有单进程时钟回归测试仍保留，新工具用于独立诊断并输出原始值。

bench/macos_bench.py 新增可选 rusage_info_v4 进程指令数、周期数，在每个阶段开始/结束读一次，不在 20 ms 内存采样循环中增加调用。缺失、不支持或非单调计数保存 null；检查进程出生标识以拒绝退出/复用 PID。计数边界在原 CPU/内存边界外侧，存在微小时间差。没有改变 CPU 计算、负载、帧率和内存口径。

ABI 通过当前 Xcode SDK 头文件编译出的 C 程序验证：结构体大小 296，instructions 偏移 248，cycles 偏移 256，与 ctypes 相同。脚本语法检查及 14 项 bench 测试通过；组合源码 cargo fmt --all --check 和 workspace all-targets Clippy 再次通过。SDK 验证程序和结果在 abi-check.json，时钟原始值在 clock-check.json。采样全部结束后才运行检查和编译。

## 六次独立 GUI 运行

100×30，Menlo 10，1200 帧、60 Hz；before/after、after/before、before/after 交错。通过 Computer Use 按专用 bundle ID 自动选择正在运行的测试包，每次启动和两个 TUI 阶段前都 Raise + 点击标题并验证终端焦点。本批次 6 次成功启动、18 个前置记录，未恢复旧样本、未观测到额外测试实例，完成后测试进程均退出。没有连续遮挡监测。每次运行的客户端哈希、服务端哈希、格子尺寸、TUI 字节数与帧数均核对一致。

三对全屏客户端指令数稳定下降，中位数 4.0813→3.3296 十亿，约 −18.42%。服务端指令数维持约 2.23–2.28 十亿，同一客户端版本的指令数也比 CPU 时间稳定。但客户端周期数并非三对都下降，CPU 总占用中位数 11.660→13.549%，不能把指令数下降等同于 CPU 占用、耗时或能耗改善，也不能用不变服务端归一化消除所有环境差异。局部 TUI 客户端指令数约降低 1–2%，CPU 时间仍混合方向。

历史 footprint 每对均减少，中位数 130.455→118.080 MiB，减少 12.375 MiB（9.49%）。内存收益复现。combined/ 保存完整原始结果和审核数据，包括 CPU 更差的配对，没有筛选最好样本。

## 当前结论与下一步

空 metadata 表优化的减指令机制在组合版真实 GUI 中成立，紧凑历史的内存收益也重复成立；整体 CPU 占用的稳定改善仍未得到证明。保留候选而不合入 main、推送或替换安装。此前 CPU 单项三对的 −4.42% 结果是独立实验，不能移植到组合版。

下一步应使用组合版的 profile 找到剩余实际耗时，重点核查 GPU 提交/驱动与渲染路径，而不是继续仅靠同样的 CPU 百分比多跑几次或把指令数当最终胜利。当前不具备完成 CPU 优化验收的证据，目标继续保持 active。
