# 历史快照与输入延迟：候选回退与局部撤回

## 结论

全量流式历史编码（69f0097）确实增加了 resize 压力下的输入尾延迟。现在 tick 已恢复旧的 snapshot-then-unlock-encode 路径；首次连接/切换会话等原来已在锁内编码的路径仍用 prepared snapshot。开发分支尚未合入 main、未安装或推送。

局部撤回后的 p99 接近原版，但 p95 尚不能认定等价：Unicode p95 在三轮中仍高于同期原版。不能宣称全面消除了响应回退，也不能把早先 headless 快照约 16 MiB 节省当作修订版 daemon 的已验证收益。tick 的大历史更新又会构造 PackedCell 数组，需重新测实际应用的内存。

## 方法与边界

使用独立真实 daemon、100×30 网格、私有 PTY 的 Python worker。先输出 10,030 行并等待终端解析标题完成标记，确认当前历史为 10,000 行。每个新进程先测空闲，再每 16 ms 在 29/30 行之间切换窗口高度，强制完整历史替换；客户端持续读取帧，验证历史行数并计数。每阶段 1,000 条输入，目标间隔 2 ms，阻塞时跳过过期时刻，序号逐条校验。没有丢失、重复或乱序，压力阶段每次至少 50 次完整历史替换。

计时范围：发送 ClientMessage::Input → daemon → PTY worker 读取 → Unix datagram 回执。包括客户端 writer 等待、OS 调度与 Python 回执，不包括屏幕绘制；是闭环单条在途诊断，不是输入到像素延迟或开环负载模型。周期性的输入和 resize 可能产生相位效应，p95 的波动不能隐藏。

plain/Unicode 各三轮新进程；每轮交替 before/after 顺序。两个批次各自包含原版控制组，不能直接把不同批次绝对数值相减当收益。第二批客户端仅增加 Unix 平台包装及结束时 reader 状态检查；输入、resize 参数相同，二进制哈希分别记录。测试期间未并行编译。锁屏不影响该项纯 headless 服务端诊断，但此数据不能代替四终端前台 GUI 对照。

## 验证与复现

219 项 protocol/server 测试通过；workspace clippy 和 fmt 通过（保留既有警告）。release 编译通过。额外的预热 smoke 不计入表格。所有私有进程已清理；未操作用户运行中的 GUI、daemon 或 PTY。

测试工具：`bench/history_input_latency.py` 与 `crates/loom-protocol/examples/history_input_latency.rs`。使用相同功能构建两套 server，保存独立二进制，再运行：

```sh
cargo build --release -p loom-protocol --example history_input_latency
python3 bench/history_input_latency.py --before /tmp/before/loomtty-server --after /tmp/after/loomtty-server --output /tmp/loom-hil-new --rounds 3
```

输出目录必须为新的短路径（macOS Unix socket 长度限制）。原始 JSON 保留每条样本、阶段耗时、历史替换数量、daemon 资源计数和二进制哈希。资源覆盖整个进程的两个阶段，不能据此推导单独阶段 CPU。四终端 corrected-output 对照与前台 profile 仍待解锁和前置确认。
